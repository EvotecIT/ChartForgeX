# Agent Guide: ChartForgeX website and hub content

## Purpose

This folder builds **chartforgex.com**, a PowerForge.Web site (`site.json`, `pipeline.json`, `themes/chartforgex`). It is the canonical home for ChartForgeX docs, examples, the gallery and the API reference. evotec.xyz lists ChartForgeX as a `dedicated-external` product and redirects its former `/projects/chartforgex/` docs, API and examples routes and `/demos/chartforgex/` to the matching pages here, so keep those routes stable: docs under `/docs/<slug>/`, examples under `/examples/<slug>/`, API types under `/api/<type-slug>/` with the default `.html` aliases, and the gallery at `/gallery/`.

## Build

```powershell
pwsh Website/build.ps1 -Serve            # dev pipeline + local server on :8080
pwsh Website/build.ps1 -CI               # CI-mode pipeline (engine lock, verify baseline, audit, optimize)
```

`build.ps1` locates PowerForge.Web.Cli from `-PowerForgeRoot`, `POWERFORGE_ROOT`, a sibling `PSPublishModule` checkout, or the global `powerforge-web` tool. Use `-SkipBuildTool` to reuse an existing engine build.

Enabled features: `docs`, `notFound`. Prism highlighting is self-hosted under `static/assets/prism` (MIT, see its `LICENSE.txt`); the site makes no third-party requests.

## Sources of truth

- `content/pages/`: home, gallery, Mermaid, PowerShell, PowerBGInfo and 404 pages. Front matter only for data-driven layouts.
- `content/project-docs/docs/`: documentation shared with the hub. Use relative links between docs and examples so they resolve on both `/docs/` and `/projects/chartforgex/docs/`.
- `content/examples/`: curated examples shared with the hub.
- `data/home.json`, `data/mermaid.json`: home and Mermaid page copy. Keep claims aligned with the README and `docs/mermaid*.md`; do not claim complete Mermaid compatibility.
- `data/gallery.json`, `static/examples/generated/`: the generated gallery, refreshed by `build/Sync-GeneratedExamples.ps1`.
- `data/hero.json`, `data/visuals.json`, `static/site/`, `static/apple-touch-icon.png`, `themes/chartforgex/partials/generated/`: generated by `tools/SiteVisuals`. Never hand-edit them.
- `data/examples.json` (example cards: outcome, mode, surface, key) and `data/docs.json` (docs map topics and the surface-table rows): hand-maintained copy for the examples index and docs pages.
- `themes/chartforgex/`: layouts, partials and CSS. `assets/tokens.css` is the only token source (site and API reference) and mirrors `ChartForgeX/Themes/Tokens/evotec.chartforgex.tokens.json`; `assets/base.css` holds the shared components (masthead, code block, prose, tables), `nav.css` holds the header navigation, and page CSS lives in `docs.css`, `pages.css` (atlas, steps, figures, examples, docs map), `gallery.css`, `home.css`, `playground.css`, `powerbginfo.css` and `api.css`.

## Design system

Every inner page is built around output ChartForgeX renders itself. Visuals come from `tools/SiteVisuals` through `data/visuals.json`; never hand-draw a chart or diagram in a template.

- Navigation: the `main` menu in `site.json` is the source of truth. Top-level items are groups (Product, Developers) with `Items`; each destination has an `Id` (its thumbnail in `static/site/nav/`), a one-line `Description` and `Meta.key` (series colour 1 to 6, `hollow` past six). `partials/header.html` renders each group as a disclosure button and panel; the group holding the current page shows that page as a keyed chip. The header and footer are one source for every page, including the API and command references: the theme renders them at `/api/` and `/powershell/commands/` (`content/pages/*-chrome.md`, layout `chrome`), `build/Export-ApiChrome.ps1` lifts them out after the site build, and the API docs steps wrap their pages in them before overwriting those two routes. Keep every header slot the same size on every page; the current page is marked by a key in its group button and a chip after the groups, so nothing moves between pages. Do not style the header or footer per page.
- Landing pages (gallery, Mermaid, examples, docs index, PowerShell) open with `partials/stage.html`: a band that stays dark in both themes, the title beside real output in a `.cfx-output` window. `stage_wide = true` sets the output full width under the title row, for output that needs the room; Mermaid uses it for its source and render.
- Output is never covered by other artwork. Source shown with what it renders uses `.cfx-pair` (base.css): the source as wide as its longest line, the output beside it, stacked with the output first below 1180px. Code that goes with a large render sits under it, as on the home hero. Reference pages open with `partials/masthead.html`: a plot grid aligned to the content edge, the title set like a chart title and an axis rule with ticks. Do not add eyebrow labels above either.
- Tabs, toggles and filters use one component, `.cfx-seg` (base.css): each option has a `.cfx-key` swatch with `--key`, a label and an optional `.cfx-count`. The selected option sits on the card surface with its key colour drawn underneath; that rule is the only motion. `.cfx-seg--legend` drops the tray for long legends.
- All code uses one component: `<figure class="cfx-codeblock" data-lang="…">` with a `cfx-codeblock__bar` caption (language, optional file name, `cfx-codeblock__actions`) and a `pre > code.language-…`. The figure is the frame and the bar is opaque; the `pre` is its own scroll area under the bar, so a block limited by a height (or `--cfx-code-max`) scrolls without passing under its caption. Markdown fences and the examples on API and command pages are wrapped at runtime by `site.js`, which also adds the copy action and highlights with the self-hosted Prism (`window.cfxHighlight` for code set later). Add missing grammars to `static/assets/prism/components/`.
- Programs read as annotated steps: `partials/steps.html` splits rendered Markdown at each H2 and sets the step's prose beside its code. Keep one code block per step. Examples and the Mermaid guide use it.
- Docs figures use the `cfx-figure` shortcode (`id`, `ids` for a strip of frames, or `frame` for a live HTML output, plus `caption`); figures come from `data.visuals.docs.figures`, and each render links to its full-size file. The surface table on "Choose a rendering surface" gains an output per row from `data/docs.json`; if a row's text changes, update that file or the table renders without outputs.
- Code colours follow the page theme. Bands that stay dark add `cfx-tone-dark` so code and series colours keep their dark values.
- Category keys use the six Graphite series colours in order; past six, keys turn hollow rather than taking new hues.
- Generated gallery programs keep gallery-only setup in a `#region Setup` block. The viewer hides that region and offers the full program as a download.
- `static/fonts/`: self-hosted Archivo and JetBrains Mono with their OFL licences.
## Regenerating site visuals

The hero chart, its surfaces, the Markdown fence, Mermaid samples, the touch icon, the social card and every inner-page visual (navigation thumbnails, the Mermaid family atlas, docs figures, example outputs, the gallery and not-found charts) are rendered by ChartForgeX itself:

```powershell
dotnet run --project Website/tools/SiteVisuals -c Release -- Website
```

Rerun it after renderer changes that affect visible output, then inspect the home, Mermaid, examples and docs pages in both themes before committing. The generator owns `static/site/{atlas,nav,docs,examples,gallery,pages}` and clears them on each run.

- Mermaid atlas families, their copy and their sources live in `data/mermaid.json`. A source is `playground:<sample id>` (`tools/Playground/PlaygroundSamples.cs`), `fixture:<name>` (`tests/mermaid-conformance/fixtures/`) or `site:<name>` (`tools/SiteVisuals/Mermaid/`). A family's `title` names its render when the source has none (front matter for the playground, the family's render options for the atlas). Atlas renders lay out on a 4:3 canvas with the family name as subtitle, then `VisualOutput.Fit` crops each to what it draws so it fills its card; prefer sources whose shape suits that card. Families listed under `recognised` must still be diagnostic-only; the generator fails when one starts rendering.
- `tools/SiteVisuals/ExampleVisuals.cs` mirrors the code on each page under `content/examples/`. Change both together.
- A `ChartGrid` or `VisualGrid` themes its panels, so set `WithThemeMode(mode)` on the grid itself; a mode set only on the panels renders light panels in the dark files.

## PowerShell examples

`/powershell/` and the home PowerShell band show ImagePlayground scripts next to the files and console output they produced. Nothing on those pages is hand-written output, and the pages do not link to example scripts elsewhere.

- `powershell/<id>.ps1` and `powershell/examples.json`: the scripts and their titles, families (`flagship`, `charts`, `diagrams`, `stories`) and optional `show` file. Keep lines under about 68 characters (85 for the flagship) so cards need no horizontal scrolling, and end each script with output worth reading, such as `Format-Table -AutoSize`.
- `data/powershell-examples.json` and `static/powershell/examples/<id>/`: generated by `build/Render-PowerShellExamples.ps1`. Never hand-edit them.
- `data/imageplayground.json`: generated by `build/Sync-ImagePlayground.ps1` from the module manifest.
- `data/powershell.json` (page copy and the ImagePlayground panel) and `data/powershell-roadmap.json` (coverage rows marked `available`, `partial` or `planned`): hand-maintained. Test a capability against the published module before marking it available.

Run both scripts against the same published ImagePlayground release, not a source build:

```powershell
Save-Module ImagePlayground -Path D:\Dev\Scratch\ip-module -RequiredVersion 3.3.0
$module = 'D:\Dev\Scratch\ip-module\ImagePlayground\3.3.0\ImagePlayground.psd1'
pwsh ./Website/build/Sync-ImagePlayground.ps1 -ModulePath $module
pwsh ./Website/build/Render-PowerShellExamples.ps1 -ModulePath $module
pwsh ./Website/build/Render-PowerShellExamples.ps1 -ModulePath $module -Id service-map, org-chart
```

Without `-ModulePath` both scripts use the newest installed ImagePlayground. To preview a release before it reaches the PowerShell Gallery, point `-ModulePath` at an ImagePlayground checkout with `IMAGEPLAYGROUND_DEVELOPMENT=1` and pass `-ModuleVersion` with the version it will ship as; do not publish pages rendered that way until that version is on the Gallery. The renderer runs each script in a fresh `pwsh -NoProfile` with the en-US culture and pins both `Set-Location` and the process directory to the example's output folder, because ImagePlayground resolves relative `-FilePath` values against the process directory. A failing script stops the run. Check the generated images and the total size of `static/powershell/examples/` before committing; prefer SVG over GIF for animation.

## PowerBGInfo wallpapers

`/powerbginfo/` tells one story: twelve finished wallpapers (a few in full with their code, the rest as gallery cards, and the ones rendered for other screens), one wallpaper built step by step, the data block and its sources, the theme presets, regions and widgets, what ChartForgeX draws, getting started and running it in production. Every image is the output of a PowerBGInfo script, rendered with `-Target File`; nothing on the page is a mock-up. The page follows the newest PowerBGInfo source, even before it is released, and records the commit it was rendered from.

- `static/powerbginfo/*.png`, `static/powerbginfo/scripts/`, `static/powerbginfo/features/` and `data/powerbginfo-showcase.json`: generated by `build/Sync-PowerBGInfo.ps1` from the `manifest.json` and PNG files that PowerBGInfo's `Examples/Run.BGInfo.Showcase.ps1` (scenarios) and `Examples/Run.BGInfo.Features.ps1` (theme presets, regions, widgets) write. Each scenario's script, its data block, its line ranges and theme preset are read from the PowerBGInfo commit that produced the renders, and the data file records that commit. Of the scenario renders it copies the 1920 x 1080 pair and the `-ScreenSizes` renders (3440 x 1440 and 1080 x 1920); it skips 2560 x 1440, which the page never shows larger than 1240 pixels. `scripts/<file>.txt` is each script for the viewer, which slices its Presentation and Data tabs out by line. Never hand-edit them.
- `powerbginfo/steps.json`, `powerbginfo/steps/*.ps1` and `powerbginfo/sources/*.ps1`: the build-it-yourself steps (each a complete script), the timeout example and the data-source snippets, hand-maintained. `build/Render-PowerBGInfoSteps.ps1` runs every step against a PowerBGInfo build, diffs it against the step before it (or its `base`) and writes `static/powerbginfo/build/` and `data/powerbginfo-build.json` with the commit. It fails on a line over 79 characters or a snippet that does not parse. Never hand-edit its output.
- `data/powerbginfo.json`: page copy, alt text, the featured scenarios, the uses that group and filter the scenario cards (every scenario belongs to one), the screens shown at other sizes, the widget one-liners and crops, the ChartForgeX parts and the production routes, hand-maintained. Each widget `crop` is a rectangle in pixels of the 1920 x 1080 feature render; check the crops after a sync. Keep widget one-liners under about 52 characters so they fit a third of the content width, and run every snippet against the module before changing it.
- Production guides are linked through one constant, `production.guideBase` in `data/powerbginfo.json`; every route, note and guide entry adds only its file name. Change that value when the guides move.
- The get-started steps in `content/pages/powerbginfo.md` are hand-maintained; run the preview script with `-Target File` before changing it.
- The navigation thumbnail is a crop of the admin workstation render, made by `tools/SiteVisuals`; rerun the generator after a sync.
- The scenario cards and the viewer are the gallery's `gallery-card` and `gallery-dialog` partials with `gallery.css`; the page sets the viewer's language, link labels, image sizes and stacked layout before including the dialog. The viewer shows the card's own image for the page theme, so it uses the WebP variants the optimize step wrote for that image.
- The optimize step writes WebP variants of `powerbginfo/**` at 480 (cards), 960 and 1440 (figures and the viewer) pixels and points the page at them; the PNG files stay as the full-size links. Images below the stage load lazily, and each figure and card loads only the current theme's file.

Build PowerBGInfo from source into a scratch folder (never into the checkout), against a ChartForgeX snapshot when it needs unreleased ChartForgeX changes, then render and sync from the same commit:

```powershell
git -C C:\Support\GitHub\PowerBGInfo archive <commit> | tar -x -C D:\Scratch\pbg
dotnet build D:\Scratch\pbg\Sources\PowerBGInfo.PowerShell\PowerBGInfo.PowerShell.csproj -c Debug -f net8.0-windows `
    -p:ChartForgeXProjectPath=D:\Scratch\cfx\ChartForgeX\ChartForgeX.csproj
pwsh -NoProfile -Command "& D:\Scratch\pbg\Examples\Run.BGInfo.Showcase.ps1 -OutputDirectory D:\Scratch\out\showcase"
pwsh -NoProfile -Command "& D:\Scratch\pbg\Examples\Run.BGInfo.Features.ps1 -OutputDirectory D:\Scratch\out\features"
pwsh ./Website/build/Sync-PowerBGInfo.ps1 -RepositoryPath C:\Support\GitHub\PowerBGInfo -Ref <commit> `
    -RenderPath D:\Scratch\out\showcase -FeaturePath D:\Scratch\out\features
pwsh ./Website/build/Render-PowerBGInfoSteps.ps1 -ModulePath D:\Scratch\pbg\PowerBGInfo.psd1 `
    -RepositoryPath C:\Support\GitHub\PowerBGInfo -Ref <commit>
dotnet run --project Website/tools/SiteVisuals -c Release -- Website
```

Every PowerBGInfo example writes files only. Do not run any of them with `-Target Wallpaper`, `-AllUsers` or `-Target LogonScreen` while preparing the site.

Run the CI-mode pipeline and check the home, gallery, docs and Mermaid pages at desktop and phone widths in both themes. A local build does not prove that chartforgex.com has deployed the change.
